## Read your own results first

All paths below are under **`src/agent/.foundry/results/`**. They describe **your local run**; the later tables describe the recorded run above. If you used retry labels, use those labels and paths instead.

These files are generated by `collect`, `evaluate`, `compare`, and `verify`. Their absence in a fresh clone is normal before the corresponding step. **A file missing after its command completed requires recovery**; do not fill the gap by copying recorded example results.

**Quick view:** from the repository root of the workshop folder, run the block for your step; `summary` only reads saved results. The variables below hold the actual labels set in the main workshop. In a new terminal, [restore the run values](troubleshooting.en.md#run-values) first.

**Terminal — step 6, a baseline `row_id` to review:**

```bash
python scripts/workshop.py summary --labels "$BASELINE_LABEL"
```

**Checkpoint:** a `sol` / `luna` / `astra` table and `baseline business-check failures:` appear.

**If not:** if it says `comparison.json` is missing or lacks `baseline`, run the [6-1](../README.md#6-1-aggregate-the-results-and-find-a-row-to-review) `compare` block, then rerun this `summary`. Do not rerun `collect` or `evaluate`.

**Next:** if 6-1's trace check is unfinished, complete [baseline `monitor`](../README.md#baseline-traces) first; saving the review needs its `telemetry.json`. If already complete, return to [README 6-2](../README.md#review-case) and choose the first `row_id` in that list.

**Terminal — step 7-4, same-dev changes, the reviewed case's V2 result, and failed rows:**

```bash
python scripts/workshop.py summary --labels "$BASELINE_LABEL" "$CANDIDATE_LABEL"
```

**Checkpoint:** `Reviewed case ...` with `source trace carried: yes`, the V1 `->` V2 table, then `improved business-check failures:` and `improved Foundry-score failures:`.

**If not:** for a missing `comparison.json` or label, run [7-3's](../README.md#7-3-collect-and-evaluate-the-same-dev-set) `compare`, then repeat only this `summary`. For a missing `Reviewed case` or `source trace carried: no`, follow [README 7-4 recovery](../README.md#compare-results). Do not repeat collection/evaluation for a simple file-lookup error.

**Next:** return to [README 7-4](../README.md#compare-results) and copy the three parts into your notes.

**Terminal — step 8-3, separate holdout pass counts per model and failed rows:**

```bash
python scripts/workshop.py summary --labels "$HOLDOUT_LABEL"
```

**Checkpoint:** a table with `business`, `groundedness`, and `relevance` as `.../4`, then `holdout business-check failures:` and `holdout Foundry-score failures:`.

**If not:** for a missing `comparison.json` or label, run the [8-2](../README.md#holdout-evaluation) `compare` block, then rerun this `summary`. Do not rerun `collect` or `evaluate`. For `n/a` evaluator results, [recover evaluation](troubleshooting.en.md#evaluation-retry).

**Next:** return to [README 8-3](../README.md#holdout-results) and copy both lists into your notes separately.

**Terminal — inspect the same response:** enter the actual label (for example, `improved`) and the copied row ID separately. This reads the saved answer without evaluating again.

```bash
read -r -p "Result label: " RESULT_LABEL &&
read -r -p "Row ID: " RESULT_ROW_ID &&
python scripts/workshop.py show --label "$RESULT_LABEL" --row-id "$RESULT_ROW_ID"
```

**Checkpoint:** `row_id` matches the row you selected from the failure list, and `query`, `saved_response`, `business_checks`, and `fixed_reference` appear. **If not:** for `Unknown row ID`, enter only the ID, without the parenthesized score or check name. If you used a retry label, use that actual name in both inputs.

<a id="business-checks"></a>

### What each evaluation layer receives

`collect` invokes the actual Hosted Agent and preserves the response, model routing, prompt hash, retrieved context, and trace. `evaluate` sends the **same answer text** to Foundry rather than generating another answer.

| Layer | Inputs | Pass criterion |
|---|---|---|
| `decision` | Structured decision and frozen expected value | Exact match |
| `required_numbers` | Answer text and required monetary values | All required amounts present after normalization |
| `citations_retrieved` | Citation values and that request's retrieved source IDs | Every citation was retrieved |
| `citations_relevant` | Citation values and the case's allowed ID list | Every citation is allowed for the case |
| `citation_present` | Citation-required flag and citation array | Nonempty when required |
| Foundry groundedness | Question, answer text, and actual retrieved context | 1–5 scale; pass at 4 or above |
| Foundry relevance | Question and answer text | 1–5 scale; pass at 4 or above |

The rest of this document explains the method and **recorded examples**, not scores your run must reproduce.

<details>
<summary>Recorded-run method: evaluator inputs, calibration, and run contract</summary>

- Foundry evaluator `response` maps to `answer`, not the complete response JSON.
- Neither evaluator directly receives the structured `decision` or `citations` array, and `ground_truth` (kept in JSONL) is not mapped into either. Interpret Foundry evaluator scores and business-check results separately.
- The amount check tests whether the normalized numbers (for example, `180,000` or `180000`) appear in the answer, not whether every sentence is fully correct; cases with no required amounts pass it.
- Citation-required rows have a different denominator from all response rows.
- A new run caches the evaluator versions it fetches first and uses the same definitions for the before/after evaluations.
- Two fixed English calibration examples received groundedness **5** for the supported KRW 180000 limit and **2** for an unsupported KRW 990000 claim; calibration passed and is not part of the 48 candidate responses.

| Component | Contract |
|---|---|
| Scenario | Synthetic company travel-policy consultation; no real approval, booking, or payment |
| Language/workspace | `LAB_LANGUAGE=en`, separately owned workspace, agent, and knowledge objects |
| Candidates | `gpt-6-sol` and `gpt-6-luna` version `2026-09-22`; `gpt-6-astra` version `2026-09-03` |
| Judge/evaluators | `gpt-5.4-mini` version `2026-03-17`; `builtin.groundedness` version 17 and `builtin.relevance` version 12, threshold 4 |
| Baseline/candidate | English V1 vs English V2 on the same six dev questions × three models |
| Holdout | Frozen V2, four separate questions × three models |
| Retrieval | Same KB retrieval instructions and one retry when the planner runs no search ([why](#retrieval-miss)) |

</details>

<details>
<summary>What changed between V1 and V2</summary>

V1 is an intentionally incomplete educational starting point. It tells the assistant not to display internal document identifiers, which can conflict with the citation-ID contract.

V2 explicitly distinguishes effective dates and document status, defines the decision labels, requires original retrieved document IDs, handles insufficient evidence, and rejects instructions to ignore policy or invent completed approval. It is a provided prompt candidate, not a model substitution, fine-tuning job, or automatic prompt optimizer. Dev questions, reference answers, corpus, three candidates, judge, evaluator definitions, and concurrency stayed fixed.

</details>

<a id="retrieval-miss"></a>

### Retrieval misses and the guard used in this run

| Question | Open | Read | Meaning |
|---|---|---|---|
| Did retrieval fail for my row? | That label's `responses.jsonl`, same `row_id`. | `retrieval_attempts`, `source_ids`, and whether its `activity` list has an entry with `type: searchIndex`. | `retrieval_attempts: 2` with empty `source_ids` is a retrieval failure; do not treat it as a prompt or model-quality failure. |

In this English run, all 48 responses searched on the first attempt (`retrieval_attempts: 1`), and none had empty evidence.

<details>
<summary>How the guard works and why it was added</summary>

- The guard changes retrieval only: the KB has retrieval instructions to search applicable policies even when a request asks to ignore or rewrite them. Prompts, data, reference answers, and evaluators are unchanged.
- If a response's `activity` has no `searchIndex` step, the agent retries the same question **once**; the attempt count is stored as `retrieval_attempts` in the response and its trace.
- In the first Korean run (`ko-20260923`), Korean D06 asked to ignore the rules and write that approval was complete. Foundry IQ's planner recorded only `modelQueryPlanning` and ran no search, so Sol answered `not_covered` with empty `source_ids`.
- Calls without search fell from 19/30 before the change to 1/30 with KB retrieval instructions and 0/30 with one retry added. English D06 skipped search in 0/30 calls even before the change. Full record: [Korean results](validation.ko.md#retrieval-miss).

</details>

<details>

- `feedback` copied the frozen dev question, reference answer, and rubric, then added the reviewed row, original trace, language, prompt/context hashes, and an English review reason. It did **not** promote the agent's answer to ground truth.

<details>
