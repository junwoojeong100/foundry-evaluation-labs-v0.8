## 후속 검증 — 승인받은 남은 작업

사용자가 남은 작업을 승인하고, 화면에 제시한 실제 원본 D01 응답 두 개의 검토 결과도 확인했습니다. 금액과 `allowed` 판단은 맞지만 `TRAVEL-2026` 대신 문서 제목을 인용한 실패입니다. 원본 trace ID를 가진 별도 사람 확인 파일을 남겼고, 이전 `assistant` 검토 기록은 그대로 보존했습니다.

보존했던 두 기반 환경에 새 이름의 hosted 에이전트를 준비했습니다. SDK 2.3.0, 후보 모델 버전, 지침, 정책, 평가기 정의와 기존 응답 파일은 유지했습니다. 후속 트래픽을 원래 언어별 48응답에 더하지 않습니다.

### 연속 평가 결과와 한계

확인한 권한 수정은 [공식 최소 역할](https://learn.microsoft.com/azure/foundry/concepts/rbac-foundry#minimum-role-assignments-to-get-started)에 명시된 **프로젝트 managed identity의 부모 Foundry 계정 범위 Foundry User**입니다. 프로젝트 범위 Foundry User와 직접 OpenAI 접근만으로 대체하는 안내는 불완전했습니다. Owner 부여·키 인증·SDK 업그레이드는 사용하지 않았습니다.

| 검증한 자동 실행 구성 | Trace 행 | Relevance | Task adherence | Indirect attack | 실행 오류 |
|---|---:|---:|---:|---:|---:|
| 한국어 후속, 20:24:54 UTC | 20 | 20/20 | 20/20 | 20/20 | 0 |
| 영어 분리 judge, 20:53:03 UTC | 20 | 20/20 | 20/20 | 20/20 | 0 |

**영어 결과는 구분해서 해석해야 합니다.** 기존 공유 judge 구성에는 권한 반영 후에도 간헐적인 일반 `AuthenticationError`가 남았습니다. 같은 배포를 사용하는 새 평가 정의에서도 오류 한 건이 남았습니다. 이후 별도 구성에서 **같은 `gpt-5.4-mini` / `2026-03-17`, Global Standard 100, 동일한 RAI 정책**의 분리된 judge 배포를 사용했습니다. 대상 에이전트와 프로젝트 identity는 같고, 자동 실행은 고유 trace 20개·유효 결과 60개·오류 0건으로 완료됐습니다.

이전 실패 정의·run·출력은 모두 비공개 증거에 보존했습니다. 성공한 분리 구성과 직전 실패 구성의 자동 선택 trace는 20개 중 8개만 같으므로 **짝지은 인과 비교가 아닙니다.** 별도로 구성한 실행 경로의 성공을 확인한 것이며, 배포 분리만이 원인을 해결했다거나 기존 공유 배포가 소급 복구됐다거나 앞으로 간헐 오류가 절대 없다고 보장하지 않습니다. 일반 인증 오류를 정상적인 낮은 점수로 바꾸거나 좋은 점수를 얻으려고 유효한 평가를 반복하지 않습니다.

평가 정의를 만들기 전에 공식 권한을 준비합니다. 기존 환경에서 계속 오류가 나면 설정·오류 증거를 보존하고 소유자가 조사하거나, 별도 이름과 승인을 갖춘 분리 검증을 수행합니다. 진행한 실험의 judge를 몰래 바꾸거나 `continuous.json`을 지워 성공처럼 보이게 하지 않습니다.

### Red team과 유료 GitHub CI

별도 모델 스캔의 ASR은 영어 실습 환경 **2/6**, 한국어 실습 환경 **0/6**이었습니다. 첫 한국어 스캔은 서비스 상태가 `completed`인데도 한 위험 범주가 빠져 있었고, 원본 metadata를 남긴 뒤 별도 완전한 실행 한 번으로 확인했습니다. 소규모 모델 대상 스캔이지 RAG 에이전트 전체의 안전성이나 언어별 안전 성능 차이를 증명하지 않습니다.

승인된 비공개 저장소에서 실제 릴리스 워크플로를 GitHub-hosted runner로 실행했습니다. OIDC 임시 user-assigned identity에 구독 Reader와 두 검증 계정 범위 Foundry User만 부여했습니다.

| CI 집단 | 기본 응답 / trace | V1 → V2 업무 통과 | Holdout | 별도 에이전트 직접 평가 | 게이트 결과 |
|---|---|---|---|---:|---|
| 영어 | 48 / 48 | 0/18 → 18/18 | 12/12 | 18행 | Red team 2/6 공격 성공으로 올바르게 차단 |
| 한국어 | 48 / 48 | 0/18 → 18/18 | 12/12 | 18행 | 템플릿의 명시적 continuous 예외를 적용해 통과 |

두 `evaluate` 작업은 실제 증거 검증과 자기 소유 평가기 정리까지 완료했습니다. 영어의 빨간 게이트는 유효한 안전성 발견이며 초록색을 얻으려고 재실행한 실행 오류가 아닙니다. Continuous 예외는 **이 별도 CI 워크플로 내부에서만** 적용하며, 프로젝트 identity의 실제 예약 평가는 따로 실행했습니다.

CI는 새 응답을 수집하지만 같은 공개 교육용 `dev`·`holdout` 문항을 쓰는 별도 실행이지, 새로운 미사용 검증 데이터가 아닙니다.

CI가 이전 검토 이유를 새 응답에 복사할 때는 이제 `feedback --reviewer automation`을 사용합니다. 새 CI 응답을 사람이 다시 검토한 것처럼 표시하지 않으며, 수동 CLI의 기본 `human`은 유지합니다.

### 최종 정리와 보관 증거

후속 일정 네 개, 복원한 에이전트 두 개, 후보 배포 여섯 개, Search 객체 여섯 개와 해당 소유 역할을 정리하고 확인한 뒤 기반 환경을 삭제했습니다. 임시 CI identity·federated trust와 구독 Reader를 포함한 CI 역할 할당 세 개도 제거했습니다.

소유권·현재 자원 목록을 대조하고 명시적 승인을 받은 뒤 **전용 Azure 리소스 그룹 두 개를 삭제하고 실제 부재를 확인했습니다.** 기존·분리 judge, Search, 관측 자원도 함께 삭제됐습니다. 원래 공유 환경과 관계없는 전역 Azure CLI 설정은 보존했습니다. 앞선 `check-cleanup` 파일은 기반 환경이 아직 있던 중간 경계의 결과이며, 그룹 삭제 뒤 값을 고쳐 쓰지 않았습니다.

비공개 CI 저장소는 읽기 전용으로 보관하고 두 run의 artifact도 로컬에 내려받았습니다. `.workshop/`에 원본·후속 소스 manifest, 구성별 실패·성공 기록, 사람 확인, 포털 검증, CI 산출물, 삭제 확인을 보관했습니다. 원본 산출물은 이 공개 저장소에 커밋하지 않습니다. 어떤 결과도 운영 승인을 뜻하지 않습니다.
